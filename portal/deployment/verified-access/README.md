# Verified email required before portal access

The pinned upstream allowed invited users to enter before verifying email. The API overlay now enables Better Auth's `emailAndPassword.requireEmailVerification` and organization's `requireEmailVerificationOnInvitation`. New unverified signups receive no session; password sign-in rejects them until verified. The shared private `AuthGuard` also requires `user.emailVerified === true`, covering existing sessions and failing closed if the field is missing. Public endpoints and account-level deletion remain separately governed; no schema changes or credential rotation occur.

The frontend redirects unverified sessions away from portal, dashboard and setup layouts. Its invitation page sends the canonical confirmation callback with the invitation ID, shows a pending-email screen after signup, and accepts the invitation only after verification. The confirmation component reads actual session state rather than trusting `verified=true`; it offers a Continue to portal link that completes invitation acceptance in the correct organization. Existing-account invitation acceptance remains supported through sign-in.

The digest-pinned API build runs six focused guard cases before compilation: anonymous rejection, existing unverified session rejection, missing flag rejection, verified/no-org rejection, verified member admission and explicitly public route admission. `runtime/test/atrium-auth.check.mjs` now expects no signup session before mail verification. Both application builds pass. React effects use an unmount cancellation check; invitation acceptance has no dependency on form fields. No secret is passed into client components.

`deploy.py` publishes the image and permits only Task/Service changes in the CloudFormation change set. Existing network, roles, secrets, task count, load balancer and database stay in place. Prior deployment/image/template references are retained here. `deployment.json` records the current API image and task definition; web references are in `../web-app/deployment.json`.

Browser receipts separately cover existing-session denials, new-signup/login denials, and captured-mail verification through confirmation, invitation completion and fresh client login. The collector uses temporary source-group-only port 1080 access and RSA-encrypted logs, has no task role, deletes only synthetic recipient mail, and removes its task definition/network access afterward. Review accounts and concurrent operator changes must be preserved during fixture cleanup.

Driver notes: initial browser evaluation raced a full-page navigation; bounded wait retries now tolerate destroyed navigation contexts. The first invitation attempt hit the team form during hydration and correctly routed the verified admin to the dashboard. That disposable account was removed. The final driver waits for the client-specific input and asserts the stored invitation role is member before signup. The first collector receipt is retained separately; no application behavior was changed to accommodate the driver.

Final cleanup: all synthetic users, invitation, memberships, projects and organization are removed, and its Storage prefix is empty. The 52-table readonly audit observed concurrent changes only in retained review sessions and projects; those changes were preserved and global byte-for-byte equality is not claimed. Local temporary credentials, capture keys/links and the browser container were removed. Final HTTPS/service audit passes after collector ingress revocation.
