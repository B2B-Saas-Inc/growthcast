# Limited staging ingress

`staffBoundary` is the staging route gate, exercised by the actual HTTPS browser fixture. It requires one exact private origin-proof header before passing a request to the existing session/CSRF/database authorization. Duplicate or missing proofs are refused. Forwarded identity/source headers are discarded; the authenticated proxy boundary supplies the configured portal host.

Only catalog/artifact reads and client, recipient, document draft, PDF upload, preview and approval mutations are allowed. Guest pages, unlocking, guest downloads, manual version registration, dispatch creation, revocation and PIN issuance are unavailable in this limited release. No mail transport is connected.

Three direct HTTP tests cover ingress proof failures, disabled route/method variants and forwarded-header spoofing. Thirteen full HTTPS browser checks run through this same gate. A separate candidate Node image is now packaged with private file configuration, verified database startup and the ten-migration guard. It is deployed to staging using the existing task volumes, with migration010 and matching recovery images. Private ingress proof is not a replacement for staff authentication; both checks are mandatory.

Mount `/run/guest` owned by that UID with mode 0700; its files must be mode 0400 and ordinary files, not symlinks. The service will refuse an unmigrated staging database. Startup does not execute migrations. No configuration values or database errors are logged. SIGTERM closes the listener and database pool with a bounded shutdown. No mail transport is linked.

## Candidate delivery runtime composition

The candidate now supports explicit `GC_DOCUMENT_DELIVERY=staging-verified`. Omission or `disabled` retains the deployed staff-only behavior; unknown values refuse startup. Enabled startup additionally requires migration013, private `/run/signing/delivery.json` and the existing `/run/delivered/material/application-secret-env.json` from the API. ## Candidate gateway and lifecycle services

The same image now packages the gateway entrypoint `gateway-start.mjs` (port3003) and separate lifecycle entrypoint `lifecycle-start.mjs` (port3004 readiness only). Both services are now deployed to staging with separate roles. The gateway reads private `/run/gateway/connection.json` with exact `url`, `projectRef`, `ca`, `environment` fields and requires gc_gateway. It fixes the staging public/provider origins and portal embed parent. Its543-path asset allowlist is generated from the exact pinned upstream image at build time.

Lifecycle reads private `/run/lifecycle/config.json` containing `connection`, `providerToken`, `teamId`, `encryptionKey` (64 hex), and `storageConfiguration`, plus `/run/lifecycle/signing-trust.pem`. It requires gc_lifecycle and migration013, polls the restricted pending-completion function, verifies the canonical PDF using packaged OpenSSL, stores it and publishes its original-project attachment. It receives no SMTP settings or recipient PIN records. Both entrypoints use the same private-file ownership/mode checks as staff runtime. Version-pinned secret delivery and separate task roles are deployed.
